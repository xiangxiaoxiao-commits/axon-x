结论：问题不是「本体不够」，而是已写好的机制从未拿到数据。溯源覆盖率 0.1% 的根因不是代码缺失——会话蒸馏早就调用 stampRelationMetadata——而是陈旧缓存永远等不到回填。修掉这一条之后，本机真实数据的关系溯源覆盖率从 0.1% 变成 100%，且关系总数与文件数一条没变。

01最关键的那个发现

评估阶段我看到「245 个缓存里 243 个是旧 schema」，当时的判断是「重跑一次建索引就好」。这个判断是错的——查下去发现重跑也修不了：

IndexProject 只能回填它「重新扫描到」的会话

缓存升级的入口是会话发现：扫描 ~/.claude/projects、~/.codex 等目录 → 对每个会话检查缓存 schema → 过期就回填。但本机 245 个缓存里有 238 个的源会话文件已经不存在了（Claude Code 清理旧会话、换过机器）。

这些「孤儿缓存」仍然通过 LoadAllCache 参与每一次组图——assembleGraph 读的是全部缓存文件，与会话发现无关——但它们再也不会被任何一次建索引碰到。于是 schema 升级只覆盖活着的少数会话，孤儿永远是旧 schema、永远没有溯源。

这条路径是结构性的，不是靠用户多点一次「建索引」能绕开的。

召回结果可审计：直接命中 vs 关联线索

关系扩展带进来的实体，此前和查询直接命中的实体混在一起渲染，agent 无法分辨「图谱就是这么说的」和「这是从图上跳过去的」。现在 retrieve.Result 记录每个实体是怎么被找到的——经哪条边、第几跳、是否反向——输出据此分成两段：

### main.resolveEntities（function）        ← 直接命中：完整渲染事实

关系：
- app.go —包含→ main.startup（置信度 100%，来源：代码仓库）

关联线索（通过关系扩展加入，非直接命中；需要时再单独查询）：

分开渲染顺带修掉一个实际后果：关联实体如果也展开断言，会占满结构区预算（1600 字符），把直接命中的断言挤掉。实测一次查询从 1 个种子扩展出 20 个实体——答案是 1 个，噪音是 19 个，而预算全被噪音的标题吃掉。

04过程中我自己犯的一个错，以及它暴露的真问题

第一版实现让 axon 命名空间的关系从 3623 条翻倍到 7184 条

原因：SaveCache 用 sanitizeFileName(SessionID) 推导文件名，而真实数据里存在 mcp:1786602946922-0d231da5.json 这种带冒号的文件名，冒号会被改写成下划线。迁移读到 mcp:….json，却写到了 mcp_….json——原文件没被修，同时又多出一份同样的知识，每次组图都把这份知识算两遍。

这是只有拿真实数据跑才会暴露的问题：单元测试里文件名都是我按 SaveCache 的规则生成的，永远不会出现这种不一致。我是靠对比「迁移前后关系总数」发现的。

修法：新增 saveCacheFile 接受显式路径，迁移回写它读到的那个文件；并加回归测试，用真实存在的冒号文件名构造场景锁死它。

这条值得记下来：评估阶段的数字是我自己算的，实现阶段的数字也得用同一把尺子重新量一遍——两次量法不一致，翻倍这种量级的错误就会被当成"改进"。

05召回侧的两处改动（行为变化，需要你知情）

这两条改变了召回的返回内容，不只是数据质量，所以单独说明。

1. 反向扩展：只沿已声明的逆属性

原来的实现只走正向，注释写的理由是「反向会污染上下文」。但查下去根因不是取舍失误，是缺少区分能力——没有逆属性声明时，系统无法分辨「调用↔被调用」这种合法反向和真正的污染，只好一律禁止。

代价是量化的：axon 命名空间 48.8% 的关系只能从主语侧召回，而盲区恰好落在语义最易命中的具体技术名上——graph.Dir、claudedata.extractText、main.TestResumeCommandNewline。问「graph.Dir 是什么」时，正向扩展一无所获；而此刻最有价值的「谁调用了它」全在入边上被挡掉。查询越具体，越容易踩进盲区。

现在：正向照旧全部走，反向只走已声明的逆属性（调用↔被调用、包含↔属于、依赖↔被依赖…）。未声明的（如 相关）仍然不反向——有测试锁住。信任闸门在两个方向上都照常生效。

2. 传递扩展：限制在已声明的谓词上

跳数从 1 提到 2，但第 2 跳只允许 包含/调用/依赖/属于/前置于。这样多出来的可达性是「A 传递包含/调用/依赖 C」，而不是任意两跳链的闭包。

这也回应了评估里的一条约束：不要物化传递闭包。包含 有 864 条边且是代码目录树，物化会随树深爆炸；查询期有界遍历才是对的。

如果你觉得这两条改动太激进

把 internal/retrieve/retrieve.go 里的 expandHops 改回 1，反向扩展就只剩第 1 跳生效（即只走声明的逆属性、不做传递）；再把 expandAlongRelations 里 declaredInverse 那个分支去掉，就完全回到原行为。词表与迁移不受影响——它们是独立的两块。

06没做的，以及为什么

没有引入 OWL DL 推理机

这本书自己在 §1.1 结尾警告过：「很多企业的本体项目做不下去，第一步就错了——用 OWL 把所有东西都建模了，结果推理机跑几个小时跑不完。」Axon 是端侧单机 Go 程序，图规模千级实体。所以只做 RDFS 级词表 + 两条有界遍历，够吃下全部收益。

句子式标签只做「标记 + 预防」，不自动改写

还有 974 条标签超过 6 字（约占 14%），健康度会显示这个数字并提示复核，但不自动改写。判断「约束修改后需检查真正的谓词是什么」需要语义判断，机器猜一个 相关 塞进去反而丢信息——那正是评估里提醒过的陷阱。要真正收敛这批，需要过一次模型（单独一步，可以后做）。

不过未来不会再产生新的了：蒸馏提示词已经写明 label 必须是 2–8 字谓词，整句进 evidence。

三档治理仍未激活（评估里的第 4 项）

关系状态目前还是 asserted 一档到底、置信度 0.85。原因是旧缓存里 LLM 从没输出过 state/confidence——这两项不可能靠回填恢复，必须重新蒸馏（要花 LLM）。本次没有动它。

注：来源感知的信任分级（代码 → verified）已让状态机第一次有了 verified 数据，但 candidate 档仍为空——那要靠重新蒸馏。

试过、然后撤回：超长标签的前缀折叠

我实现过一版「前缀折叠」：把「谓词 + 限定」折回谓词（部署到 sit-49 → 部署于，限定进 evidence）。先跑了数据模拟，结论是「剩余 ≤ 8 字」可折 150 条。

但模拟里发现它会误伤，而且正好踩中我自己上一轮定的原则：

提供活跃任务数据  → 提供   // 名词性限定，折得对
约束修改后需检查  → 约束   // 动词从句，折了就凭空造出一条关系

两者的剩余部分都是 6 个字，长度区分不了名词短语和动词从句——要安全就得先做词性判断。为 15% 的收益引入分词依赖不值得，而且这恰恰是评估报告里写过的陷阱：「机器猜一个谓词塞进去反而丢信息」。

所以撤回了，词表保持只做精确匹配，剩下的交给人工复核或将来过一次模型。这个取舍写进了 schema.go 的注释，免得以后有人再试一遍。
