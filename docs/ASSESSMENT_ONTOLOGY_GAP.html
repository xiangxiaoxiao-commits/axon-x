对照《当LLM不够用了——本体推理的企业决策实践》的方法论

评估对象：本机 ~/Library/Application Support/axon/graphs 中的真实图谱数据（只读分析，未修改任何数据）

12 个命名空间 / 10 个有数据 2,866 个实体 4,293 条关系 6,265 条断言 2026-10-15

一句话结论：Axon 的问题不是「本体不够」，而是已有的治理设施大部分处于空转状态——三档状态机从未触发、溯源写入率 0.1%、置信度是一个常量。真正该做的不是引入 OWL（书里自己警告过那会拖垮推理），而是把已经设计好的机制接上数据流。

02必须修正的上一轮判断

我上一轮把「关系 label 同义割裂」列为首要改动，数据不支持这个判断。

实测同义组只有 19 组、125 条边，占全部关系的 2.9%。按核心语义归一后（剥掉「于/在/到」等虚词）能合并的最大一组只有 39 条边。这个规模不足以成为优先项，应当降到最后。

另一个被高估的判断：我说「声明逆属性的价值在于让双向边不再各自为政」。实测真实逆属性对极少——包含↔属于、承载↔部署于、承载↔部署到，每种只出现 2 次。所以逆属性的价值不在「合并已有双向边」，而在「合成缺失的反向方向」（让反向遍历成为可能）。原文的因果说反了。

03数据真实暴露的问题（按证据强度排序）

严重3.1 溯源写入率 0.1%，README 的核心承诺未兑现

载体总数带 sources带 evidence覆盖率
关系4,293330.1%
断言6,2653,143—50.2%
实体 obsSources2,8662,216—77.3%

根因已定位到代码行，不是推断：

  • graphbuild.go:833 那处 Sources: resolveSessionTitles(...) 属于 KnowledgeMatch —— 它是召回返回值的结构体，不是关系写入。会话蒸馏在写关系时根本没有设置 sources 字段。
  • 全仓只有两处给关系的 Sources 赋过值：cmd/axon-mcp/remember.go:121（MCP 实时写入，即那 3 条）和 codegraphbuild.go:73（v0.4.2 新增，但缓存陈旧，见 3.2）。
README 第 14 行宣称「🛡️ 可信关系 — 关系带来源、证据、置信度和审核状态」。实测关系层的四个字段里，只有 confidence 被写入（且是常量），sources 与 evidence 是 0.1%。
这本书 §1.4 的整个论证建立在一句话上：「每个结论都可以追溯到本体的公理和原始数据。」—— 这条恰恰是书的核心，也是 Axon 自己 README 的核心，但没兑现。

重要3.2 code 缓存陈旧，3,556 条边的身份未升级（不是代码缺陷）

现象：静态代码解析出来的边落盘为 asserted / 0.85 / 无 sources，但 README 的信任策略表写的是 verified / 1.00。查证结论是数据陈旧，不是 bug：

引入时间git 确认该行由 e9229d3（v0.4.2）于 2026-09-18 引入
缓存时间graphcache/axon/code:graph.json 时间戳 2026-08-17，早于该修复一个月
缓存内容3,556 条关系全部无 state / confidence / sources

这是本次评估里性价比最高的动作

零代码改动，只需重建一次 axon 命名空间的代码索引。收益：3,556 条边升级为 verified / 1.00 并带上 sources，直接把 3.1 的溯源覆盖率从 0.1% 拉到约 83%，同时让 3.3 的状态机第一次有 verified 数据流过。

注意：wanlian 命名空间没有 code 缓存文件，其代码知识来源需另行确认。

重要3.3 三档状态机与置信度分级从未被触发

字段实测分布设计意图
关系 stateasserted 4,125 · 空 168 · verified 0 · candidate 0 · rejected 0四档生命周期
断言 stateasserted 6,265（100%）四档 + 人工审核覆盖
关系 confidence0.85 × 4,122（96.1%）· 0.9 × 3 · 无字段 1680–1 证据强度

后果是连锁的：

  • RelationUsableForRecall（relation.go:55，门槛 state ∈ {asserted,verified} && conf ≥ 0.65）实测放行 4293 / 4293 = 100%。这个"闸门"目前不过滤任何东西。
  • README 说的「弱关联只展示、不进入事实召回」——因为没有任何一条关系落到 candidate，这个特性在生产数据里从未运行过一次。
  • MergeRelationTrust 的 relationStateRank 排序逻辑同理：没有数据能触发状态升降。
  • 健康度面板的「可信 / 候选 / 冲突」统计，实际只有「可信」一档有值。

这不是缺陷，是设计了但没接上数据流的能力。它与 3.1 同源：写入端不区分证据强度，只写一个默认常量。

重要3.4 label 承载了整句断言，谓词退化为句子

590 条边（13.7%）的 label 长度 ≥ 9 字，共 295 个不同句子。这些不是关系类型，是把整个事实写成了谓词：

// 真实数据，取自 grapds/*.json
gaia-lite      --写入 mesh-source-user-name，并透传 mesh-source-inst-id-->  Mesh.context att
经办人身份      --在无 identityId body 时依赖 token 体现-->              上架类接口
connector_node --缺失时导致 currentNodeInfo 为 null-->                  dataResourceRegi
月度计量分页接口 --通过EXISTS执行digitalContractId过滤-->                deliver_order
订单业务单号     --subjectNo匹配approvalSubjectNo-->                     审批查询参数映射

为什么这是问题：

  • 无法归一、无法校验——谓词每次都是新的，建立不了词表，也就没有治理的抓手。
  • 无法参与任何推理——逆属性、传递性都建立在"谓词可复用"的前提上，句子式谓词天然不复用。
  • 方向语义被稀释——README 要求"关系有方向，读成通顺的话"，这些 label 确实通顺，但它们描述的是断言的完整内容，而不仅是一个方向。

修法与 3.1 是同一件事

正确做法不是删掉这些句子，而是拆分：规范谓词进 label，整句挪进 evidence。例如 connector_node --(缺失)→ Registration，evidence 记「缺失时导致 currentNodeInfo 为 null」。

这样一次改动同时解决两个问题：谓词回归可复用（label 收敛），以及 evidence 覆盖率从 0.1% 提升——信息一点没丢，只是归位了。

中等3.5 传递未闭合 1,323 条，但不能物化闭包

存在大量真实的两跳链，而图里没有对应的直接边。样例（均已核实存在）：

// axon 命名空间 ·「调用」
main.startup  --调用-->  config.Load      --调用-->  graph.pathFor
// 但缺少：main.startup --调用--> graph.pathFor

// axon 命名空间 ·「包含」
.             --包含-->  searchapp.go     --包含-->  main.IndexSearch
// 但缺少：. --包含--> main.IndexSearch

这正是书 §1.1 给出的 owl:TransitiveProperty 例子（p(x,y) ∧ p(y,z) → p(x,z)）。但有两条约束必须遵守：

  • 不要物化闭包。1,323 / 4,293 = 31% 的膨胀，而 包含（821 条）是代码目录树——闭包会随树深增长，几百个文件的仓库很容易炸成几万条边。
  • 正确做法是查询期有界传递遍历：只对白名单 label（包含 / 调用 / 依赖），只多做一跳，只在语义种子足够具体时触发，结果标记为 derived 并携带来源链。

也就是说：查询越具体，越容易踩进盲区。Agent 问「graph.Dir 是什么」，语义命中的是 graph.Dir 这个汇点，正向扩展一无所获；而此刻真正有价值的上下文恰恰是「谁调用了它」——全部落在入边上，被这条规则挡掉了。

根因是上一轮已经定位的那处注释与实现矛盾：retrieve.go:253 的文档说 "treating relations as undirected"，实现却只走正向。缺 owl:inverseOf 这类声明，系统无法区分「合法反向」与「污染反向」，只能一刀切全禁。所以这不是取舍失误，是缺少区分能力的必然妥协。

06明确不做的

不引入 OWL DL 推理机（HermiT / Pellet 那类）

这本书自己在 §1.1 结尾警告过：「很多企业的本体项目做不下去，第一步就错了——他们用 OWL 把所有东西都建模了，结果推理机跑几个小时跑不完。正确的做法是从 RDFS 开始，只把真正需要推理的部分用 OWL 公理表达。」

Axon 是端侧单机 Go 程序，图规模千级实体，引入完整描述逻辑推理是纯粹的过度工程。RDFS 级 + 少量公理 + 硬规则足以吃下上述全部收益。

也不该照搬这本书的产品形态

书面向企业级决策平台（Palantir、中数睿智），默认你有专职本体工程师和数月的认知工程预算。Axon 的约束完全相反：端侧、单机、用户不会去写 Turtle 语法。

所以 Axon 的正确定位不是「本体工程工具」，而是「本体约束的自动编译 + 校验器」——从既有图谱反推 label 词表、逆属性表、传递候选，让用户点几下确认。这也是为什么本报告全部建议里，没有一条要求用户「建立 TBox」。

评估方法：直接读取本机真实图谱数据（graphs/*.json 与 graphcache/*/code:graph.json），全量统计而非抽样；所有代码结论均定位到具体文件与行号，并用 git 佐证引入时间。未修改任何图谱数据。
