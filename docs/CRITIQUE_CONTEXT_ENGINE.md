# 批判：给 axon 加「原文 chunk 通道」真能让 AI 懂业务吗？

> 立场：唱反调。目标是在动手前把方案的失效点、隐含假设、被忽略的更根本原因全暴露出来。
> 结论先行：`RESEARCH_OBSIDIAN_GAP.md` 的诊断「丢了原文 → 补原文 chunk」在**类比层面是错的**，在**工程层面是高风险低确定收益的**。不是不能做，而是**顺序错了**：应先证伪更根本的失效原因，再决定要不要做这件重活。

---

## 0. 先厘清一个被诊断悄悄偷换的前提

诊断的核心论证是一个类比三段论：

1. Obsidian 有效，因为它召回并注入「原文块」；
2. axon 无效，因为它只注入「蒸馏实体」；
3. 所以 axon 补上「原文块」就会有效。

**这个类比的第 1 步就偷换了概念。** Obsidian 的「原文」和 axon 的「原文」不是同一种东西：

| | Obsidian 笔记 | axon 的「原文」= Claude Code 历史对话 jsonl |
|---|---|---|
| 谁写的 | **人**主动写下、反复修订 | 人随口说 + **AI 长篇输出**，各占一半甚至 AI 更多 |
| 意图 | 沉淀、供未来检索 | 完成当下任务，用完即弃 |
| 信噪比 | 高（已是人脑蒸馏的产物） | 低（充斥试错、被推翻的方案、纠正、寒暄、重复复述） |
| 结构 | 自包含的段落/块，语义完整 | 一问一答的**流**，单条消息离开上下文常常不成立 |
| 事实性 | 人背书 | **AI 自己说的话**，可能含幻觉/当时就错的结论 |

**关键洞察：Obsidian 笔记本身就已经是「蒸馏产物」——只不过蒸馏器是人脑，且蒸馏结果被保留成了原文。** axon 的对话记录是「蒸馏之前的原料」。所以「Obsidian 保留原文所以有效」这个观察，真正说明的是**「保留高质量的、被确认过的浓缩内容」有效**，而**不是**「保留任意原文」有效。

诊断把「原文」当成了褒义词，其实在 axon 语境下，「对话原文」约等于「未过滤的原料」。**照搬「注入原文块」，等于把 `extractPrompt` 辛苦滤掉的噪音（工具日志之外的那些：废话、试错、被否方案、AI 的长篇自说自话）又原样灌回上下文。** 这不是移植 Obsidian 的成功机制，而是移植了一个 axon 数据形态并不支持的表面动作。

> **如何规避/验证**：动手前先做一次「肉眼审计」。随机抽 5 个真实 session 的 jsonl，人工按 600–1000 字切 10~20 块，逐块标注「这块单独注入给 AI，是帮助 / 无关 / 有害（含被推翻的旧方案、AI 的错误结论）」。如果「有害+无关」占比超过一半，方案的地基就是塌的。**这个审计半天能做完，比写代码便宜得多。**

## 1. 质疑一：「加原文 chunk 就能有效」不成立——注入的是原料，不是知识

### 1.1 对话原文里，AI 自己的输出是最大的污染源

`buildTranscript`（`graphbuild.go:267`）保留的是 `user` + `assistant` 的文本。在 Claude Code 的会话里，**assistant 的文本体量通常远大于 user**：大段方案讲解、代码解释、"我将要做 X"、"让我检查 Y"。这些一旦按字符窗口切块入库，会造成三重问题：

- **自我循环喂食**：把 AI 过去生成的话，当成「业务背景」再喂给 AI。若当时的结论是错的、或后来被推翻，这个错误会被固化成"知识"反复注入。蒸馏这一步本来还能靠 LLM 判断"这个方案被否了别留"，直接切块**丢掉了这层判断**。
- **信噪比进一步恶化**：assistant 的礼貌性/过程性话术（"好的，我来看一下…"）在对话里占比极高，embedding 会把它们和真正的决策混在一起。
- **代码块的双刃**：对话里贴的代码往往是**片段/草稿/被改掉的版本**，不是仓库里的最终态。注入过时代码比不注入更危险——而仓库最终态已经由 `codegraphbuild.go` 这条独立通道覆盖了。

### 1.2 有一处现成的证据说明「原文里能提炼的东西本就不多」

axon 已经有 `extractPrompt`，它对每个 session 跑一遍 LLM，指令是"宁可少而准""没有值得入图的知识就返回空数组"。**如果一个 session 蒸馏后经常返回空或寥寥几条，那恰恰说明这个 session 的原文里本来就没多少持久业务知识**——那么把它的原文切块入库，召回时注入的也只能是噪音。诊断没有回答一个致命问题：**用户的对话里到底有多少「原文密度」值得召回？** 如果答案是"不多"，chunk 通道就是给噪音建了个索引。

> **如何规避/验证**：统计现有 cache——有多少 session 蒸馏出 0 个实体、有多少 ≤2 个。这个分布直接告诉你「原料里有没有矿」。如果大量 session 是空的，问题根本不在"丢了原文"，而在"原文里就没货"。

## 2. 质疑二：召回准确性——短查询 × 长噪音块 × 中英混杂，大概率召回"似相关实为噪音"

看清楚 axon 的**召回查询长什么样**，这是诊断完全没讨论、却决定成败的一环：

- **commit 场景**（`commit.go:194` `buildKnowledgeQuery`）：查询 = 变更文件路径 + 目录 + 文件名 + hunk 里的符号名。这是一串**关键词**，不是自然语言，例如 `orchestrate.go orchestrate runEnrich buildExecMessages`。
- **enrich 场景**（`orchestrate.go:259` `enrichQuery`）：查询 = 用户潦草的任务描述（可能就一句话）+ scope 路径。

现在要用这种**短、关键词化、代码符号为主**的 query，去 embedding 召回**600–1000 字、中英混杂、含大段口语**的对话块。这是 RAG 里最难的一类匹配：

- **查询-文档长度极不对称**：短 query 的向量语义被少数 token 主导，长 chunk 的向量被稀释，cosine 相似度既不稳定也不可解释。
- **中英 + 代码混合**：实体名是中文（"支付服务"），代码符号是英文，对话是中英夹杂。同一个 embedding 模型对这三种分布的表示质量参差，`knowledgeSeedMinScore=0.35` 这个阈值在这种混合分布下几乎是拍脑袋。
- **"似相关"陷阱**：对话里反复讨论同一模块的多个片段，其中有当前有用的、有过时的、有被否的，它们的 embedding 高度接近。召回 topN 很可能把**同一话题的过时/错误片段**一起捞上来——比只召回实体摘要更危险，因为实体摘要至少是被 LLM 判过一次的"结论"。

学界证据不站在诊断这边：

- 一项跨模型规模的实证研究发现，**任何检索注入（哪怕是 oracle 最优检索）都会破坏 42–100% 原本答对的题**，且这种"分心效应"是由**上下文的存在本身**驱动的，而不只是质量差（[arxiv 2603.11513](https://arxiv.org/html/2603.11513)）。
- "干扰段落会让 LLM 答错"是 RAG 的已知顽疾（[The Distracting Effect, arxiv 2505.06914](https://arxiv.org/pdf/2505.06914)；[Rethinking Relevance, CEUR](https://ceur-ws.org/Vol-3802/paper23.pdf)）。
- 亚马逊的研究直接指出：**support ticket / chat log 这类非结构化沟通做 RAG，效果受"原始数据本身"限制**，他们的方案是先用多智能体把它**结构化**成知识库，而不是直接切块（[Amazon Science](https://www.amazon.science/publications/from-unstructured-communication-to-intelligent-rag-multi-agent-automation-for-supply-chain-knowledge-bases)）。注意：axon 现在的"蒸馏成实体"**恰恰就是这条被业界推荐的路**，诊断却把它当成病根要砍。

> **如何规避/验证**：别猜召回质量，测。拿 10 个真实 commit / enrich 查询，人工标注"理想应召回哪些片段"，跑一版 chunk 召回，算 precision@5。如果 precision 低于 0.5，注入 = 拉低而非提升。同时务必做**关掉 chunk 注入 vs 打开**的 A/B 对照，别只看"打开后感觉好像详细了"。

## 3. 质疑三：token 预算——注入点是"短产出"，塞原文块性价比尤其差

看注入落到哪里：

- **commit 消息**：`MaxTokens:1500`，产出是一条 <72 字的 subject + 简短 body。base 模型光靠 diff 就能写得不错。
- **任务 spec**：`MaxTokens:2000`，产出是结构化 JSON。

这两个都是**短、收敛、低自由度**的产出。往它们的上下文里塞进 5 个 600–1000 字的原文块（≈3000–5000 字，中文 token 更贵），意味着：

- **信噪比对产出的边际收益很低**：commit 消息本来就该"忠于 diff、别编造"（`commitSystemPrompt` 明确这么要求）。塞一堆对话原文，反而增加模型"从背景里抄一个听起来对但和本次 diff 无关的动机"的风险，直接和"never invent facts not supported by the diff"的约束打架。
- **成本与延迟**：commit / enrich 是高频交互动作，每次多 3–5k token 的输入，累积成本和首字延迟都上去了，换来的却是上面存疑的收益。
- **挤占效应**：长上下文本身会稀释关键信息（diff / 任务描述才是主角），已有研究表明**上下文变长本身就会让模型质量和推理时延一起劣化**（[arxiv 2601.11564](https://arxiv.org/html/2601.11564v1)）。

诊断说"注入原文比实体费 token 得多"，但**没有回答"这些 token 花在 commit/enrich 这种短产出上值不值"**。我的判断：commit 场景尤其不值——那里最该注入的是**术语和动机的一句话**，正好是实体摘要能给的，原文块反而是负担。

> **如何规避/验证**：先给注入设 token 硬预算（如背景 ≤800 token），超了就截断。再分场景评估：commit 可能压根不该注入原文块，enrich（要补全隐含约束、易踩坑）才可能用得上。别一刀切全场景注入。

## 4. 质疑四（最重要）：「不好用」的真因，真的是丢了原文吗？——列出"加了 chunk 也救不了"的场景

诊断把"信息量塌缩"钉成头号根因，但它自己的证据表里，**好几条被标为"症状/隐患"的，恰恰更可能是真凶**。以下场景，**加了原文 chunk 依然不好用**：

### 场景 A：用户根本没配 embedding，全程在跑降级版（高概率）
`newEmbedder` 要求 OpenAI 协议的 endpoint，且 Anthropic 没有 embeddings API（`memory.go:13`）。只用 Claude 的用户 → `newEmbedder` 失败 → `MatchKnowledge` 静默降级为 substring 匹配（`graphbuild.go:485`）。
**加了 chunk 通道，chunk 也要 embedding 才能语义召回。没有 embedder，chunk 通道同样退化甚至直接不可用**（对 600–1000 字的块做 substring 几乎召不回）。**这条不修，做 chunk 是白做。** 而且这可能才是"不好用"的第一真因：很多人根本没意识到自己在用阉割版。

### 场景 B：中文实体名在英文 diff/代码里从不字面出现（commit 场景结构性失效）
commit 的 keyword fallback 靠 `strings.Contains(diff, 实体名)`。实体名是"支付服务"，diff 里是 `PaymentService` / `pay_svc`。**中文实体名在英文代码里字面命中概率≈0。** 一旦 embedding 也没配（场景 A），commit 场景的召回率直接归零——**和有没有 chunk 无关**。这是别名机制（aliases）该解决的，不是 chunk 该解决的。

### 场景 C：新项目 / 没历史积累（冷启动）
axon 的知识全靠从历史对话/代码/已采纳任务蒸馏。**新项目没有历史对话**，cache 是空的。加 chunk 通道，也没有原文可切。冷启动下，无论实体还是 chunk 都是空集。用户此时觉得"不好用"，根因是**没数据**，不是"丢了原文"。

### 场景 D：图谱本身没建好（关系稀疏 / 命名漂移残留）
`extractPrompt` 追求"少而准"，关系抽得稀疏；`expandAlongRelations` 只走 1 跳（`knowledgeExpandHops=1`）。就算召回到种子实体，也扩不出关联知识。chunk 通道**绕过图结构**，等于承认"图没建好"，但它并没**修好**图——只是在旁边加了个平行的、噪音更大的通道。

### 场景 E：用户的历史对话里压根没多少"业务知识"
如果用户主要用 Claude Code 做零散调试、跑命令、改小 bug（而非讨论架构/决策），那么对话里**本就没有值得沉淀的业务知识**。见 §1.2：蒸馏返回空的 session 越多，越说明这一点。此时 chunk 通道召回的只能是"上次怎么改的那个 bug"，对"懂业务"毫无帮助。

### 场景 F：截断策略本身可能有 bug（顺带发现）
`buildTranscript` 在 `b.Len() > maxTranscriptChars(16000)` 时 `break`，即**保留最早的 16000 字，丢掉后面的**。但注释写着 "newest content matters most for knowledge"（`graphbuild.go:120`）。**代码行为和注释意图相反**：长 session 被截成了开头部分。若真如注释所说新内容更重要，那现在蒸馏喂进去的就是错的一半。**这种基础 bug 不排查，加 chunk 只是在错误的原料上再叠一层。**

> **如何规避/验证**：做一张"失效归因表"。对用户报"不好用"的真实 case，逐个打标签：是没 embedder（A）？还是中文名没命中（B）？冷启动（C）？图太稀疏（D）？原文没货（E）？截断吃错了（F）？**先数一数哪个占比最高。我强烈怀疑 A/B/E 的合计远大于"信息量塌缩"。** 如果是这样，chunk 通道是排序靠后的投入。

## 5. 质疑五：有没有更有效或更简单的路子？——有，而且至少三条都比"切碎原文"更对

### 方案甲：召回「整段会话/连续片段」而不是切碎（治召回，不引噪音结构）
对话的语义是**跨轮次**的：决策的理由在三轮前，结论在五轮后。按 600–1000 字硬切，会把一个完整推理切成两半，召回半截 = 召回噪音。
更对的做法：以 **session（或话题段）为召回单元**，用已有的 session 标题/摘要做粗筛，命中后注入**该段的有界转写**（复用 `buildTranscript` 的思路，但修掉 §4-F 的截断方向），或对命中段**针对当前 query 现场做一次聚焦重述**（类似已有的 `focusPrompt`）。这样保住了上下文完整性，也让 LLM 再滤一道噪音。成本比全量切块 embedding 低，且信噪比高得多。

### 方案乙：让用户手动喂高质量业务文档（这才是真·Obsidian 机制）
Obsidian 有效的**真正原因**是"人写的高密度笔记"，不是"切块"。那就**直接对标这一点**：允许用户在项目里放一个 `AXON.md` / 业务说明文档，把它作为**第一优先级、高召回权重**的知识源，甚至整篇常驻注入（文档通常不长）。
这比"从一坨对话里蒸馏/切块猜业务"**确定性高一个量级**——因为知识是人主动、结构化写下的。诊断的机制 C（人工确认 = 高质量）其实指向的就是这条，但它排到了改进 4、优先级最低。**我认为它该排第一。** 且实现极简：读文件 + 注入，不需要 embedding、不需要切块管线。

### 方案丙：做成 MCP，让 Claude Code 按需 agentic 查询（把"塞"变成"取"）
axon 的使用场景就是配套 Claude Code。与其在 commit/enrich 时**预测性地塞**一堆可能没用的背景，不如把知识图谱/会话检索暴露成 **MCP tool**，让 Claude Code 这个 agent **在它判断需要时主动查**，并且**自己去读仓库源码文件的最终态**（而不是读对话里的过时代码片段）。
好处：(1) 召回由更强的推理主体按需触发，噪音注入的责任交给 agent 自己判断；(2) 天然避免"每次都塞、塞了也没用"的浪费；(3) 复用 Claude Code 已有的文件读取能力，绕开"对话里代码是草稿"的坑。这比在 axon 内部造一套 chunk RAG 更贴合实际工作流。

### 方案丁（最省）：强化 extractPrompt 保留"一句原文引证 + source 指针"
不建独立 chunk 通道，只让每条 observation 带**一句 verbatim 引证**和**精确的 source 定位**（session id + 大致位置，`ObsSources` 已有雏形）。需要细节时，AI/用户可顺着指针回去看原文。**这拿到了"可溯源到原文"80% 的价值，却不用承担切块入库、embedding 翻倍、噪音注入的成本。** 是"信息量塌缩"这个具体病症的最小手术。

## 6. 给决策者的排序建议（反诊断的优先级）

诊断的排序是：① 存 chunk + 召回原文（最高）→ ② 修 embedding 降级 → ③ 强化 extract。

**我主张倒过来，且先插入"验证"这一环：**

0. **先量化归因（半天到一天，零代码）**：跑 §0 的肉眼审计 + §1.2 的空 session 统计 + §4 的失效归因表。用数据判断真因到底是不是"丢原文"。
1. **修 embedding 降级这个坑（§4-A）**：这是很多"不好用"的第一真因，且是所有语义召回（含未来的 chunk）的地基。内置本地 embedding 或至少把降级状态明确告警。**优先级第一，诊断把它排第二是错的。**
2. **上方案乙（用户喂业务文档）+ 方案丁（observation 带原文引证）**：低成本、高确定性、直接对标 Obsidian 的真机制。
3. **修 §4-F 的截断方向 bug**：便宜且影响蒸馏质量的地基。
4. **只有在 0 的数据证明"信息量塌缩"确实是主因、且方案乙/丁不够用之后**，才考虑 chunk 通道，且优先用**方案甲（整段召回）而非硬切块**，并强制加 token 预算和 A/B 对照。

---

## 7. 一句话总结

**「丢了原文所以不好用」是一个诱人但没被数据支撑的诊断。** axon 的"原文"是低信噪比的对话原料，不是 Obsidian 那种人写的高密度笔记——把它切块注入，更可能是在给 commit/enrich 这类短产出灌噪音，而非喂知识。**更可能的真凶是：没配 embedder 全程降级（A）、中文名在代码里召不回（B）、原文里本就没多少业务知识（E），外加一个截断方向写反的 bug（F）。** 动手写 chunk 管线之前，先花半天用真实数据把这四个证伪掉；证伪不了，再考虑"整段召回"或"让用户喂文档"，而不是照搬 Obsidian 那个在 axon 数据形态下并不成立的表面动作。
