一句话：别名归并会融合互不相关的事物（503 次折叠里 170 次无依据），因为它按「名字/别名任意碰撞」触发，而 sameAs 是传递的；与此同时，仓库内包依赖边 100/100 条全部悬空被丢弃，因为实体按仓库相对路径命名、而 import 写模块全路径。

01别名归并会融合不同的事物

Graph.Merge 按「名字 或 别名任意碰撞」折叠实体。而 sameAs 是传递的：注册 A 的别名后，叫那个别名的实体折进 A，A 的别名又吸收下一个——链式折叠既不可逆，也没有任何记录。

为了量化，我给归并加了审计（MergeAudited 返回 MergeReport{Folds, Refused}），并用 MatchKind 记录**碰撞键对双方各是什么**：

碰撞类型次数占比性质
same-name 双方都以此命名13827.4%最安全（同一标识符）
name-as-alias 折叠方命名、目标别名15330.4%合理
alias-as-name 折叠方别名、目标命名458.9%合理
shared-alias 双方都只把它当别名17033.8%仅同名巧合 —— 损害就在这里

第三行不是任何一方的名字，只是双方共享的一个标签。真实伤害实例：

// 都别名「发布分支」→ 塌成一个节点
release/2.1.0  +  release/3.2.1

// 都别名「方案A」→ 塌成一个节点
gaia-janus 透传层补齐方案  +  审批历史查询分流方案

// 都别名「duc」→ 塌成一个节点
newhome  +  数字合约使用控制

为什么这比「多留一个节点」严重得多

融合之后，两个分支的事实混在同一个节点里，再也分不清哪条属于哪个分支。而这是不可逆的：原实体已经不存在了。

反过来，少合一次只是留下一个重复节点——它仍然可检索（关系解析走同一套名字/别名索引），随时能再合。一个错可恢复，另一个不可恢复，所以宁可选择可恢复的那种。

修法：只有碰撞键是某一方的实际命名时才折叠

新增 sharedAliasIsDesignation(key, names...)：碰撞键必须是其中一方的名字或其一部分，否则它只是双方共同贴上的标签，不折叠。用 designationKey 去掉分隔符再比较，所以 asset_info 与 assetinfo 视为同一个命名。被拒绝的折叠仍记录进 MergeReport.Refused 供复核。

⚠️ 中途踩坑：第一版规则太粗，打挂了一个已有测试——而这个失败很有价值

我最初只按「是否别名撞别名」来判断，结果 TestFusionWithConversationEntity 失败了。它编码的是正当的融合：支付服务 与 pay.PaymentService——两者都只把 PaymentService 当别名，但它其实是 pay.PaymentService 名字的一部分。

这个失败证明了我面对的不是纯 bug，而是设计取舍，并逼出了更精确的判据（加"包含"条件）。所以我把测试从"改掉它"改成"让规则更准"。

02仓库内包依赖边 100/100 条全部悬空

起因是我在量化归并时顺手量了一下「关系会不会在组装时丢」，发现 axon 命名空间丢 62%（2258/3623）。用与 Merge 相同口径的归因探针查清后，是两类原因：

丢弃原因条数性质
指向外部符号与内置函数
fmt.Errorf 103、t.Fatalf 82、strings.TrimSpace 75、main.len 72、context.Background 39		 2159 代码图的滤噪，合理
指向仓库内真实包
--依赖--> axon/internal/graph(20)、axon/internal/db(13)、axon/internal/embed(11)…		 100 真损失 —— bug

根因：包实体按仓库相对目录命名（internal/graph），而 import 语句写的是模块全路径（axon/internal/graph）。codegraph/goast.go:34 直接拿 import 原文当关系端点，Merge 的端点解析永远找不到它——于是整张包依赖骨架在组装时被扔掉。

// 实体名（packageName 由仓库相对路径得出）
internal/claudedata      ← 实体
// 依赖边的目标（直接用 import 原文）
axon/internal/claudedata   ← 永远匹配不上，边被丢弃

修法：读 go.mod，把本模块的 import 映射为仓库相对包名

新增 modulePath(repoDir) 读 go.mod 的 module 行，builder.importTarget() 把属于本模块的 import 前缀剥掉。外部 import（fmt、main.len）原样保留——它们在组装时照旧落下，那是滤噪，不是丢失。

实测（真实仓库）：依赖边 620 条，可解析 91 → 191，仓库内依赖边零悬空。新增的 TestThisRepoDependencyEdgesResolve 会持续校验这个性质。

顺带一提：2159 条外部符号边被丢弃这件事，此前没有任何地方说明过。现在归因探针把它印出来，免得下次有人（包括我）把它误判成缺陷。

04还没做的：代码图的修复需要重建缓存

别名归并的修复立即生效；包依赖边的修复需要重建代码图

归并发生在每次组图时，所以新规则已经生效（上面那对分支的验证就是证据）。但 依赖 边写在 code:graph 缓存里，要重建才会带上正确的端点。

重建入口是 GUI 的「从代码建图」，它会跑最多 40 次 LLM 业务增强（maxLLMFiles = 40）。你的 config 里配了 4 个 provider（含 openai 协议的），所以会真跑——有 token 成本，我没有擅自执行。

要么你点一下「从代码建图」，要么告诉我，我来触发。
