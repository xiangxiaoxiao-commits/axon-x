# Axon 产品需求文档 —— 多任务并行 AI 开发编排 + Review 工具 (PRD_ORCH)

> 事实源:`docs/BRIEF_ORCH.md`。本 PRD 在其已确认方向上细化到可开发、可测试的粒度,不推翻已确认方向。

## 1. 产品概述

Axon 是一个**桌面端、多模型的 AI 开发任务编排 + Review 工具**。你用一句/一段话粗略描述一个开发任务,Axon 先用模型把它**自动补全/详细化**成结构化规格(目标、背景、约束、涉及范围、验收标准、易漏点),把补全结果**交给你 review 和编辑**,确认后再提交给你选定的模型执行;多个任务可以**并行跑**,完成后你逐个**审阅结果**,决定采纳、打回重跑或带反馈迭代。

- **给谁用**:重度用 AI 干活的工程师/技术负责人。手上常同时压着多个任务(改 bug、写模块、出方案),习惯把活拆给 AI 并行推进,再逐个把关交付。
- **解决什么核心痛点**:**人写任务描述时天然会漏信息**——漏背景、漏约束、漏验收标准、漏涉及的文件/模块。模型拿到模糊需求就跑偏,产出返工。Axon 在"提交给模型"之前强制插入一个**信息补全环节**,把人脑里没写出来的上下文补齐、结构化,让模型拿到的是一份完整规格而不是一句模糊话。
- **差异点**:
  - 市面 AI 编码工具大多是"输入即执行"——你写多糊,它就跑多糊。Axon 把**"补全→人 review 规格→再执行"**做成强制且可编辑的一步,把返工挡在执行之前。
  - **补全可结合项目业务知识**(复用已有知识图谱/检索)自动注入背景,不是通用泛泛补全。
  - **多任务并行 + 统一 Review**:不是单轮对话,而是把"派活给多个 subagent、再审交付"这套协作模式产品化。
- **形态**:延续现有 Wails(Go 后端)+ Svelte(前端)桌面应用与暖色极简 UI,复用 provider / config / secret / store / graph / search 资产。导航改为**朴素侧边栏**(神经元中枢对生产力工具不实用,已达成共识)。

## 2. 核心概念与状态机

### 2.1 核心概念

- **任务(Task)**:编排的基本单位。承载:粗略输入(rawInput)、补全后的结构化规格(spec)、选定模型、执行产出(result)、review 结论与反馈。一个任务从建立到采纳/归档,全生命周期可持久化回看。
- **规格(Spec)**:补全环节产出的结构化文档,固定字段(见 §4 P0-2)。规格是"人确认后发给模型执行"的唯一依据,可被用户编辑。
- **执行轮次(Run / Iteration)**:一次"把规格提交给模型执行"的记录,含所用模型、产出文本、开始/结束时间、打回反馈。同一任务可有多轮(打回迭代 = 新增一轮)。历史轮次可回看对比。
- **模型(Model/Provider)**:复用现有多 provider(Claude / GPT / GLM…)。补全和执行可分别选模型;不同任务也可用不同模型。

### 2.2 任务生命周期状态

| 状态 | 英文标识 | 含义 | 是否终态 |
|---|---|---|---|
| 草稿 | `draft` | 已建任务、填了粗略输入,尚未触发补全 | 否 |
| 补全中 | `completing` | 模型正在把粗略输入扩成结构化规格 | 否(进行中) |
| 待确认 | `spec_review` | 补全结果已就绪,等用户 review / 编辑 / 确认规格 | 否 |
| 执行中 | `executing` | 确认后的规格已提交模型,正在生成产出 | 否(进行中) |
| 待审阅 | `result_review` | 执行产出已返回,等用户审阅结果 | 否 |
| 已采纳 | `accepted` | 用户认可产出,任务完成 | 是 |
| 已打回 | `rejected` | 用户否决产出且未继续迭代(归档保留) | 是(可重开) |
| 失败 | `failed` | 补全或执行过程中出错(带 failedStage 标记来源) | 否(可重试) |

### 2.3 状态流转

```
                    触发补全              补全成功
   [草稿 draft] ───────────────> [补全中 completing] ───────────> [待确认 spec_review]
        ^                              │                                  │  │
        │ 改粗略输入重新补全            │ 补全失败                          │  │ 编辑规格(自环,仍在 spec_review)
        └──────────────────────────────┼──────────────────────────────────┘  │
                                        v                                      │ 确认并执行
                                  [失败 failed] <──────┐                       v
                                        │ 重试         │ 执行失败       [执行中 executing]
                                        └──────────────┴───────────────────────┤
                                                                                │ 执行完成
                                                                                v
                                                                     [待审阅 result_review]
                                                                        │      │      │
                                          采纳 │           打回并迭代(带反馈)│      │ 打回并改规格
                                              v            (新增一轮,回执行中)│      v
                                     [已采纳 accepted]  <────────────────────┘  [待确认 spec_review]
                                                          │ 打回并放弃
                                                          v
                                                    [已打回 rejected]
```

关键流转规则:
- **草稿 → 补全中**:用户点"补全/详细化"。
- **补全中 → 待确认**:补全成功;失败则进入 `failed(stage=completing)`,可重试回补全中。
- **待确认 自环**:用户编辑规格字段,状态不变,记录为草稿态编辑(未执行前可反复改)。
- **待确认 → 执行中**:用户"确认并执行",锁定当前规格版本作为本轮输入。
- **待确认 → 草稿/补全中**:用户想改粗略输入重新补全(丢弃当前规格需二次确认)。
- **执行中 → 待审阅**:执行完成;失败进入 `failed(stage=executing)`,可重试。
- **待审阅 的三个出口**:
  - 采纳 → 已采纳(终态)。
  - **打回并迭代(带反馈)→ 执行中**:反馈拼进本轮输入,新增执行轮次重跑。核心迭代路径。
  - 打回并改规格 → 待确认:回到规格编辑,再执行。
  - 打回并放弃 → 已打回(归档终态,可重开回待确认)。
- **并行**:上述状态机对每个任务独立成立;多个任务可同时处于 `completing` / `executing`。

## 3. 用户故事

1. 作为工程师,我想用一句粗略的话快速建一个任务(如"给订单服务加个超时重试"),以便不用一开始就把需求想全,先把活记下来。
2. 作为工程师,我想让工具把我的粗略描述自动补全成结构化规格(目标/背景/约束/涉及范围/验收标准/易漏点),以便看清我原本漏掉了哪些关键信息。
3. 作为工程师,我想在规格发给模型前直接 review 和编辑它(改约束、补验收标准、删不相关范围),以便执行的依据是我确认过的完整规格,而不是模型的臆测。
4. 作为工程师,我想同时并行跑多个任务并在一个列表里看到各自状态和进度,以便不用干等一个任务跑完再开下一个。
5. 作为工程师,我想在任务完成后审阅产出,并选择采纳、带反馈打回重跑或改规格重来,以便对 AI 交付把关而不是照单全收。
6. 作为工程师,我想回看历史任务的粗略输入、补全规格、每一轮产出和反馈,以便复盘、复用规格或对比迭代前后的差异。

## 4. 功能需求

优先级:**P0 = MVP 必须**(缺了闭环不成立);**P1 = 首版后紧接**;**P2 = 增强/后续**。

### P0-1 建任务(粗略输入)
- 新建入口(侧边栏"新建任务"按钮 + 列表页显眼入口)。
- 输入:一个多行文本框(粗略描述,必填)+ 可选标题(留空则用描述首行自动生成)。
- 可选:关联项目(复用现有 project 选择器,供补全环节取业务背景);不选则纯凭描述补全。
- 保存即为 `draft` 状态,立即持久化(不丢)。
- 支持一键"建好直接触发补全"或"仅存草稿稍后补全"。

### P0-2 信息自动补全 / 详细化(**核心**)
- 用户在草稿/待确认态点"补全",任务进入 `completing`,调用所选模型把 rawInput 扩成**结构化规格**。
- 规格固定字段(缺失字段模型需显式标注"待补充"而非留空):
  1. **目标(Goal)**:这个任务要达成什么。
  2. **背景/上下文(Context)**:为什么做、相关业务背景(关联项目时结合知识图谱/检索注入)。
  3. **约束(Constraints)**:技术栈、兼容性、性能、不可改动的部分。
  4. **涉及范围(Scope)**:预计涉及的模块/文件/接口;明确不在范围内的部分。
  5. **验收标准(Acceptance)**:可测的完成判据(列表形式)。
  6. **易漏点 / 风险提示(Gotchas)**:模型主动指出人类描述里常见的遗漏(边界条件、并发、错误处理、回滚等)。
- **补全结果必须可 review 可编辑**(硬性要求,非黑箱):
  - 每个字段独立可编辑(结构化编辑,非一整块纯文本)。
  - 用户可增删条目、可要求"重新补全"(可附一句补充说明重新生成)。
  - 保留"原始粗略输入"始终可见,方便对照模型补了什么。
- 结合项目知识(关联了项目时):补全 prompt 注入从知识图谱/检索召回的相关业务背景;背景来源可展示(可溯源)。未关联项目时降级为纯描述补全。

### P0-3 提交执行
- 前置:任务处于 `spec_review` 且规格已确认。点"确认并执行"→ 锁定当前规格版本 → 进入 `executing`。
- 把确认后的结构化规格拼装成执行 prompt,提交给**该任务选定的执行模型**(可与补全模型不同)。
- 不同任务可选不同模型(任务级模型选择,默认取全局默认模型)。
- **执行的定义(MVP 边界,见 §8)**:调 LLM 流式生成结果文本(方案/代码片段/答案),产出即文本,**不真正落盘改代码**。
- 执行产出流式展示进度;完成后进入 `result_review`。

### P0-4 多任务并行
- **任务列表**:所有任务一屏可见,每行显示标题、状态徽标、所用模型、更新时间。
- **同时执行**:多个任务可并行处于 `completing` / `executing`,互不阻塞(并行上限见 §8)。
- **进度反馈**:进行中任务显示进度指示(补全中/执行中 + 流式字数或转圈);列表状态实时更新。
- 支持按状态筛选(如只看"待审阅""执行中")。

### P0-5 结果 Review(采纳 / 打回 / 迭代)
- 任务进入 `result_review` 后,详情页展示本轮产出全文 + 所依据的规格。
- 三个动作:
  - **采纳**:标记 `accepted`,产出定稿,任务完成。
  - **打回并迭代(带反馈)**:填一段反馈 → 反馈 + 原规格拼成新一轮输入 → 新增执行轮次,回 `executing` 重跑(核心闭环)。
  - **打回并改规格**:回 `spec_review` 编辑规格后再执行。
- 多轮产出可回看、可对比(至少能切换查看每一轮的产出与当时反馈)。

### P0-6 任务持久化
- 任务、规格(含编辑历史至少保留最终确认版)、每轮执行产出与反馈全部落库(复用/扩展现有 SQLite store)。
- 重启应用后历史任务、规格、结果、状态完整可回看。
- 进行中任务(completing/executing)若应用退出/崩溃:重启后至少不丢已生成的部分文本,状态置为可重试(参考现有 streaming/interrupted 持久化机制)。

### P0-7 多模型选择与设置
- 复用现有 provider / config / secret:配置多家模型 key、设默认模型。
- 补全模型、执行模型可分别选(至少支持任务级选执行模型;补全模型可先用全局默认)。
- 设置页复用现有 ProviderCard / ProviderForm / SecretInput。

### P1 需求
- **P1-1 规格模板**:常见任务类型(bug 修复 / 新功能 / 重构 / 方案调研)预置补全模板,引导模型按类型补齐特定字段。
- **P1-2 批量操作**:列表多选后批量触发补全 / 批量执行。
- **P1-3 迭代对比视图**:并排 diff 两轮产出。
- **P1-4 规格复用**:从历史任务"复制规格新建任务"。
- **P1-5 补全质量反馈**:对补全结果打分/标注,沉淀 prompt 改进依据。
- **P1-6 任务标签/分组**:按项目、标签归类,列表分组。

### P2 需求
- **P2-1 真正落盘执行**:执行升级为 agent 模式,产出直接改代码/开 PR(超出 MVP 边界,重活后置)。
- **P2-2 任务依赖编排**:任务间前后依赖(A 完成后自动触发 B)。
- **P2-3 团队协作**:任务分派、他人 review。
- **P2-4 自动验收**:验收标准可执行(跑测试)自动判定采纳。

## 5. 主界面设想(点什么看什么)

整体三栏式桌面布局,导航用**朴素侧边栏**(替换神经元中枢):

### 5.1 左侧:朴素侧边栏(导航)
- 主入口:**任务(Tasks)**(默认落地页)、设置(Settings)。
- 弱化保留的辅助入口(见 §7):知识图谱、搜索等收进"更多/工具"折叠区。
- 底部:当前项目选择器 + 默认模型指示。
- 纯文字 + 图标的竖直列表,无神经元视觉。

### 5.2 中栏:任务列表(编排主视图,第一入口)
- 顶部:**"+ 新建任务"** 按钮 + 状态筛选器(全部/草稿/待确认/执行中/待审阅/已完成)。
- 每个任务一行卡片:标题、**状态徽标**(不同颜色区分草稿/进行中/待你处理/已完成)、执行模型、更新时间;进行中的显示进度(转圈或流式字数)。
- "待你处理"的任务(spec_review / result_review)视觉高亮置顶,提示"该你了"。
- 点任务 → 右栏打开详情。

### 5.3 右栏:任务详情面板(分区,随状态演进)
按任务生命周期分为可折叠分区,当前活跃分区自动展开:
1. **粗略输入区**:原始描述(始终可见,可编辑后重新补全);关联项目、模型选择。
2. **补全规格 Review 区**(spec_review 核心):六个结构化字段(目标/背景/约束/涉及范围/验收标准/易漏点),每字段可编辑、可增删条目;按钮:"重新补全""确认并执行"。展示注入的业务背景来源(可溯源)。
3. **执行区**:执行中显示流式产出 + 进度;可看本轮所用规格与模型。
4. **结果 Review 区**(result_review 核心):产出全文 + 依据规格;动作按钮:"采纳""打回并迭代(填反馈)""打回并改规格";多轮时提供轮次切换/对比。
5. **历史轮次区**:折叠列出每轮的产出、反馈、时间、模型。

### 5.4 新建任务流(点什么看什么)
点"+新建任务" → 弹出/进入新建面板填粗略描述(+可选标题/项目/模型)→ 点"补全"→ 详情面板停在"补全中"→ 完成后自动展开"补全规格 Review 区" → 用户编辑后点"确认并执行" → 面板切到"执行区" → 完成后展开"结果 Review 区"。

## 6. 验收标准(每条 P0 可测)

**P0-1 建任务**
- 输入粗略描述并保存,任务出现在列表且状态为"草稿";重启应用后仍在。
- 标题留空时,自动用描述首行生成非空标题。
- 未关联项目也能成功建任务。

**P0-2 信息补全(核心)**
- 对一句粗略描述触发补全,任务经"补全中"后进入"待确认",产出包含全部六个规格字段(目标/背景/约束/涉及范围/验收标准/易漏点),无字段整体缺失(信息不足的字段显式标注"待补充")。
- 六个字段均可编辑并保存;可增删列表型字段(如验收标准)的条目;保存后再看编辑生效。
- 点"重新补全"能基于(可选的补充说明)重新生成,原始粗略输入始终可见。
- 关联项目时,补全结果的"背景"含从知识图谱/检索召回的项目相关信息,且能查看背景来源;不可用时降级为纯描述补全且不报错。

**P0-3 提交执行**
- 仅当状态为"待确认"时"确认并执行"可点;点击后任务进入"执行中",提交给该任务选定的执行模型。
- 两个任务分别选不同模型执行,各自请求命中各自模型(可从日志/产出元信息核对)。
- 执行完成后进入"待审阅",产出为非空文本。

**P0-4 多任务并行**
- 同时对 ≥2 个任务触发执行,列表中它们同时显示"执行中"且各自独立完成,互不阻塞(其一失败不影响其二)。
- 进行中任务在列表显示进度指示;完成后状态自动更新为"待审阅"。
- 按"待审阅"筛选,只列出该状态任务。

**P0-5 结果 Review**
- "待审阅"任务点"采纳"→ 状态变"已采纳",产出定稿。
- 点"打回并迭代"填反馈提交 → 新增一轮执行(轮次+1),任务回"执行中",新一轮 prompt 含该反馈(可核对)。
- 至少能切换查看历史每一轮的产出与当时反馈。

**P0-6 持久化**
- 建任务→补全→执行→采纳全流程后重启,任务、规格、各轮产出、反馈、终态完整可回看。
- 执行中强制退出应用再重启,已生成的部分文本不丢,任务处于可重试状态。

**P0-7 多模型**
- 设置页能新增/编辑 provider 与 key,设默认模型;新建任务默认带上默认执行模型。
- 任务级切换执行模型后,执行请求使用切换后的模型。

## 7. 重构范围建议(给建议,不下最终结论)

以"任务编排成为主角"为原则,对现有功能给出取向建议:

| 现有功能 | 建议取向 | 理由 |
|---|---|---|
| 神经元中枢(NeuralHub) | **搁置/移除**,导航换朴素侧边栏 | 已达成共识,生产力工具不实用;编排主视图取代之作第一入口 |
| AI commit 提交工具(CommitView/commit.go) | **弱化保留**为辅助入口 | 与编排是两条线,短期不删,收进侧边栏"工具";后续视重合度再定 |
| 知识图谱 / 图谱构建(GraphView/graphbuild.go) | **保留并复用**(转为幕后能力) | 是"信息补全"注入业务背景的关键数据源,从独立主视图降为编排的支撑能力 |
| search / MatchKnowledge(SearchView) | **保留并复用**(转幕后 + 弱化 UI) | 同上,补全时检索项目背景;独立搜索页可弱化 |
| 会话浏览(SessionsView/claudedata) | **搁置** | 与编排闭环无直接关系,首版不作为主入口 |
| REPL(ReplView) | **搁置或弱化** | 单轮对话被"任务编排"取代,非核心 |
| 终端(TerminalView/terminal.go) | **搁置** | MVP 不落盘执行,终端暂无核心用途 |
| provider / config / secret | **保留并复用**(核心基座) | 多模型能力直接支撑补全与执行 |
| store(SQLite) | **保留并扩展** | 新增 task / spec / run 表承载编排持久化,复用现有 WAL 持久化范式 |

核心建议:**编排相关表与视图新建,不硬改现有 conversations/messages 模型**;graph/search 从"主视图"降级为"补全环节的幕后数据源";commit / sessions / repl / terminal 首版一律降为辅助或搁置,让编排主视图独占第一入口。最终保留/删除清单由架构师/项目经理裁定。

## 8. 非功能需求 + 边界

### 8.1 非功能需求
- **并行数上限**:MVP 建议同时执行(executing/completing)任务数上限 **3~5**(可配),超出排队,避免并发打爆模型限流与本地资源;需在设置暴露上限值。
- **性能/响应**:列表与状态更新本地操作 <200ms;补全/执行为流式,首字节尽快呈现,进度可见。
- **持久化可靠性**:复用现有 WAL/append 持久化范式,进行中产出增量落盘,崩溃不丢已生成文本。
- **可观测**:每轮执行记录模型、耗时、token 用量(复用现有 usage 字段);失败带 stage 与脱敏错误信息。
- **超时/降级**:调用模型设超时;失败进入 `failed(stage)` 可重试,不悬挂在"进行中"。

### 8.2 安全
- 复用现有 Keychain 存 key、错误脱敏,不硬编码密钥。
- 补全注入的项目背景仅来自本地知识图谱/检索,不外发无关代码;发给模型的内容限定为规格与召回背景。
- 关联项目路径由现有 project 选择器提供,不由任务文本任意指定,避免越权读取。

### 8.3 第一版明确不做(边界)
- **不真正落盘改代码 / 不开 PR / 不跑命令**:MVP"执行"= 调 LLM 生成结果文本,产出停留在 review 面板(P2-1 再升级为 agent 落盘)。
- **不做任务间依赖编排**(A→B 自动触发,P2-2)。
- **不做团队协作/多人分派**(P2-3)。
- **不做自动验收判定**(验收标准由人对照,P2-4)。
- **不做规格的多版本完整历史 diff**(首版至少保留最终确认版即可,完整版本树后置)。
- **不为不可能场景堆防御代码**;补全/执行失败给清晰可重试路径即可。
