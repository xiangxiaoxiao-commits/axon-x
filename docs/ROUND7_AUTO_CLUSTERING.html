01先量化：到底有几个是真的独立

两个命名空间的「实体键」（名字 + 所有别名，即检索实际使用的键）重叠到什么程度：

命名空间对共享键Jaccard覆盖较小侧
Wanlian1 ↔ wanlian 31460.98 99.7%
Wanlian1 ↔ _global_ 80.00 7.3%
其余 26 对 ≤ 80.00 ≤ 7%

这个分界干净得出乎意料：99.7% 对 7.3%，中间是一大片空白。也就是说"是不是同一个东西"这个问题在数据上毫不含糊，阈值取 50% 还是 30% 结果都一样（我取 50%，放在空白正中间）。次高的那 7.3% 还是 gaia、glite 这类通用词的偶然重合，不是真关系。

02根因：Wanlian1 是你自己导出的知识包

// wanlian 里对应的真实值
10.99.146.33

Wanlian1 独有的键全是脱敏占位符，而 wanlian 里是完整原文。结论很清楚：这是一次「导出 → 再导入」的往返——导出时按脱敏策略把内网地址和路径替换成了 <…>，同一个知识包又导了回来，于是变成了第二个命名空间。

量化的代价：两份分开是 1165 + 1003 = 2168 个实体，合并后只有 1056——重复了超过一半。这就是你感觉"知识库没归到一起"的实际数字。

03做法：按内容自动归组，界面不再要求手选

归组逻辑（新增 internal/graph/cluster.go）

  • 按内容判定，不看名字。两个命名空间的实体键重叠达到较小侧 50% 以上即归为同一「知识域」。
  • 传递：A~B、B~C 则三者同域。所以答案是连通分量，而不是逐对判断——知识包套知识包的情况也能正确归并。
  • 用较小侧做分母而不是 Jaccard：命名空间的关系通常是包含（知识包是一个项目的一部分），Jaccard 会因为大小差异而无端惩罚它。
  • 可解释：ClusterLink 保留每一对的重叠度与是否合并，所以「为什么这两个在一起」是能查的，不是黑箱。

界面：选一个命名空间，自动带上同域的

这是你诉求的核心。改动前 GraphView 的代码注释写着：

// Multi-namespace does NOT merge — user switches between them via tags
// 多命名空间不合并，用户靠标签切换

这条设计正是知识被割裂的来源。现在改成：选中 wanlian，系统自动把 Wanlian1 一起加载，并用已有的 BuildMultiGraph 合并成一张图——共享的实体合成一个节点，跨命名空间的关系得以显现。

界面上标签会标 ＋1 表示自动并入了 1 个同域命名空间，悬浮可以看到具体是哪个。你不用知道自己有 Wanlian1 这个名字。

MCP 查询同样受益

agent 问「wanlian」时也会自动扩展到整个域。否则会出现搜索能搜到、但点进去看不到的矛盾。为此统一了一个「按域取图」的入口 assembleDomain，让 search_knowledge 与 get_entity 口径一致。

实测验证（用装好的 MCP）

<内网地址>.33:80 这个实体只存在于 Wanlian1。用它做决定性测试：

一个我如实报告的观察

合并后是 1056 个实体，而 wanlian 单独就有 1170 个——变少了 114 个。这不是丢失，是 Wanlian1 带来了新的别名，让 wanlian 内部本来分开的两个节点被归并了（例如 middleware-release/gaia-lite 这条别名把相关实体连了起来）。

这正是我上一轮收紧「别名误合」规则要处理的那类操作，现在的规则只在碰撞键是某一方的实际命名时才折叠，所以是有依据的归并。但如果哪一天发现合错了，两轮改动都留了审计记录可以追。

05一个留给你的选择

要不要把 Wanlian1 从磁盘上删掉？

现在它已经不影响使用了（查询和图都会自动合并），保留它只是占一份存储。从数据看删掉是安全的：它独有的 2 个实体名、11 个键全是脱敏占位符，没有任何 wanlian 里找不到的真实知识。

但删除不可逆，所以我没有动。你说一声我就清（会先备份）。也可以就这么放着——反正你感觉不到它的存在了。
